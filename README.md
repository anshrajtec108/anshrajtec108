## ⚡ Flagship Project: APEXMATCH

### [APEXMATCH — Distributed High-Throughput Matching Engine & Asset Ledger](https://github.com/anshrajtec108/APEXMATCH)
`Node.js` • `MySQL` • `Redis` • `RabbitMQ` • `MongoDB` • `Docker`

APEXMATCH decouples the **In-Memory Matching Logic (The Hot Path)** from the **Database Persistence Layer (The Cold Path)** to handle high-frequency concurrent orders without database locking bottlenecks.


#### Active Use Case Domain: Flash Ticket Booking
*Simulating real-world scenarios like high-demand event ticketing where 50,000 users attempt to acquire 5,000 seats simultaneously.*

#### System Development Phases & Progress

- **Phase 1: Database Concurrency Control** `[COMPLETED]`
  - Implemented atomic database transactions in MySQL.
  - Used explicit row-level locks (`SELECT ... FOR UPDATE`) to isolate user wallet and balance mutations.
  - **Stress Test Verification:** Fired **100 concurrent booking requests** at a single seat item; exactly **1 request succeeded** and **99 were safely rejected**, eliminating race conditions and double-booking.

- **Phase 2: Redis In-Memory Engine & Idempotency** `[IN PROGRESS]`
  - Dockerized Redis instance running in a container environment.
  - Building an idempotency layer storing unique client `idempotencyKey` strings with a 5-second TTL to instantly drop network retry duplicates before reaching MySQL.
  - Integrating Redis Sorted Sets (`ZSET`) using `ZADD`, `ZRANGE`, and `ZSCORE` for priority-based order matching in memory.

- **Phase 3: Asynchronous Message Queuing** `[PLANNED]`
  - Integrating RabbitMQ message brokers to decouple hot path matches from persistent disk writes.

- **Phase 4: Worker Settlement & Time-Series Audit** `[PLANNED]`
  - **Ledger Worker:** Asynchronously updates finalized transactions in MySQL.
  - **Audit Worker:** Writes event logs into a MongoDB Time-Series collection for immutable compliance auditing.
